# SolidVision - AI Development Instructions

This document provides operational instructions for AI coding assistants working on SolidVision.

For architectural decisions and rationale, refer to `ARCHITECTURE.md`.

---

# Project Summary

SolidVision is a local-first semantic image retrieval system.

Users search image collections using natural language.

Images remain in the local filesystem.

The database stores only:

- metadata
- thumbnails
- embeddings
- indexing information

The filesystem is always the source of truth.

Thumbnails are files in an application cache directory
(`settings.thumbnail_directory`), not database contents: the database stores
where each one is. Nothing is ever written inside a photo collection
(RFC-028 section 10, RFC-030 section 7.1).

The project follows Clean Architecture.

```
Presentation
        ↓
Application
        ↓

```

Business rules belong only to the Domain and Application layers.

# Embedding Rules

Embeddings generated by different models are incompatible.

Each collection uses exactly one:

- model_name
- model_version
- embedding_dimension

A pgvector column has a fixed dimension.

Never mix embeddings with different dimensions in the same table.

Changing the embedding model requires a complete reindex of the collection.

# Indexing Rules

Indexing is executed by the Worker, never by FastAPI.

RFC-029 did not change that. `POST /api/v1/jobs` writes a row saying an
indexing run is wanted; a separate host process claims it and does the
work. No route opens a file, loads a model, or reaches
`IndexOrUpdateImagesUseCase`.

Processing order:

```
Filesystem

↓

Scanner

↓

Metadata

↓

Thumbnail

↓

Embedding

↓

Database
```

Incremental indexing must follow this order:

1. File exists?

2. Compare last_modified timestamp.

3. Compare file_size.

4. Only if necessary, calculate SHA256 hash.

5. Generate embedding.

Never calculate hashes before timestamp and size checks.

Collections must store:

```
indexing_jobs.last_processed_relative_path
```

to allow interrupted indexing jobs to resume safely. Relative to the
device since RFC-027, because an absolute path starts with a drive letter
and a drive letter is assigned by mount order. Compared as a path and
never as a string, and never allowed to run ahead of the batch buffer --
see `ARCHITECTURE.md`, "Resuming an Interrupted Job".

---

Worker

```
infrastructure/workers/indexing_worker.py
```

Worker entry point:

```
python -m app.infrastructure.workers.indexing_worker --root PATH
```

The `app.` prefix is required: the package is `app.infrastructure`, and
`pyproject.toml` puts `backend/` on `pythonpath`, not `backend/app/`. `--root`
is required and has no default, deliberately, so the command can never begin
indexing a real photo collection nobody pointed it at (RFC-024 section 12).

Since RFC-029 this command creates a job scoped to `--root` and runs it in
its own process. It does **not** require a second process to be running,
and it does not index the whole disk: `--root D:/fotos/2018` is still
`fotos/2018`.

The long-running executor, which the API's jobs are run by:

```
python -m app.infrastructure.workers.job_runner
```

**A host process, not a container.** The volume identity RFC-027 depends
on is a Windows construct, and a container would see a mounted path
instead. The product ships as a native Windows process with an installer,
with only PostgreSQL in a container.

Thumbnails for images indexed before RFC-030, without loading the model:

```
python -m app.infrastructure.workers.thumbnail_backfill --root PATH
```

No route accepts a file path, in any form. `POST /api/v1/images/{id}/reveal`
takes an id, builds the path on the server, and runs behind two guards
(`ALLOW_LOCAL_FILE_ACTIONS` and a loopback check) that must stay independent
of each other (RFC-030 section 6).

```

```

instead.

# Coding Conventions

Always:

- use type hints
- prefer dependency injection
- keep methods small
- keep classes cohesive
- prefer composition
- write docstrings for public APIs
- reuse existing abstractions

Never:

- create God classes
- duplicate business logic
- bypass Repository Pattern
- introduce circular dependencies
- rewrite unrelated modules

---

# Before Writing Code

Verify:

- Does this responsibility belong to this layer?
- Does an implementation already exist?
- Should this be an interface?
- Is Dependency Injection required?
- Does this respect Clean Architecture?

Prefer extending the existing architecture over introducing new patterns.

---

# Scope of Changes

When implementing a request:

- Modify only the files required.
- Preserve public interfaces whenever possible.
- Do not refactor unrelated modules.
- Explain major architectural changes before implementing them.

Consistency is more important than novelty.

# Configuration Conventions

Never hardcode configuration values (database URLs, model names, paths, batch sizes).

All configuration is loaded through:
using `pydantic-settings`, sourced from `.env`.

Access configuration only through dependency injection of a `Settings` instance — never read `os.environ` directly outside `infrastructure/config/`.
